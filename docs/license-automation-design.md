# License 每日汇总与夜间自动发放方案

更新日期：2026-09-23。依据：用户最新确认的业务流程及仓库 main（61e4e4f）。本文为设计方案，尚未修改业务代码、设置定时任务或发送邮件。

## 1. 确认的主流程

每天 09:00（北京时间）汇总待处理申请 → 发到统一 FAE 邮箱 → FAE 在线下完成市场部审批和 License 获取 → 批量上传到后台 → 每晚 20:00（北京时间）自动校对新文件 → 逐封发送到对应申请邮箱 → 保存结果。

市场部审批及 License 生成不纳入本次系统建设。后台不增加强制的在线审批关卡，也不要求 FAE 再逐封点击发送。FAE 上传用于发放的 License，是把文件交给夜间发放任务；界面应明确提示该行为。

用户已确认夜间任务为每天北京时间 20:00；09:00 沿用现有每日脚本时间。两个任务统一使用 Asia/Shanghai 时区。用户中心、在线下载和小程序改造不作为本次上线前提。

## 2. 每天 09:00：FAE 通知与状态推进

申请状态以用户最新定义为准：0 待处理（刚提交）、1 处理中（邮件成功发给 FAE）、2 已处理（上传并匹配 License）、3 已拒绝（已填写拒绝理由）。

09:00 汇总仍待通知的申请给唯一 FAE；保存本封邮件的申请成员和信息快照，SMTP 确认接受后才把原批次中的待处理申请转为处理中。失败不提前改状态；重试不混入后续新申请；结果不明不自动重发，可核查后登记结果。原脚本的状态文件只用于迁移核对，不与新发放记录混用。

## 3. FAE 批量上传

后台新增“批量上传 License”入口，支持 `.lic` 多文件以及 `.zip` 批量包。上传完成即进入夜间处理队列，并显示预计处理时间。

上传后立即做基础检查和初步匹配，让 FAE 可以提前处理问题；正式匹配与发送条件由夜间任务再次检查。上传页面显示每个文件的原始文件名、解析 MAC、候选申请、校对结果和队列状态。

文件先保存到私有存储，使用内部唯一对象名，不以原始文件名直接覆盖已有文件。记录上传批次、上传者、SHA-256、文件大小和接收时间。单批数量、大小与扩展名白名单根据真实样例配置。

只有文件完整落盘且数据库登记成功后才进入待处理状态。ZIP 上传会忽略非 `.lic` 文件，解压后最多 50 个 License、单个 1 MB、总计 10 MB；单个 ZIP 及每批 ZIP 原始大小均不超过 10 MB，ZIP 条目数上限 200，避免异常压缩包耗尽服务资源。

## 4. 每晚 20:00：校对和自动发送

任务启动时确定本次处理截止时间，领取此前已完整上传且尚未成功发放的记录。运行期间新增的文件默认进入下一晚批次，页面明确展示；可另提供管理员手动触发处理入口。

每条处理：读取文件 → 校验文件完整性 → 解析 MAC → 查找申请 → 校对唯一性和可发放状态 → 固定收件人及附件快照 → 发出邮件 → 记录结果。

### MAC 匹配规则

- 用户已确认命名规则为 `new_pds_<MAC>.lic`，其中 MAC 为 12 位十六进制字符；此前样例中的 `z` 仅为随手举例，不代表实际命名规则。
- 规范化后的内部文件名必须在前缀 `new_pds_` 与扩展名 `.lic` 之间恰好包含 12 个十六进制字符，忽略大小写。例如 `new_pds_1a2b3c4d5f60.lic` 对应 `1A-2B-3C-4D-5F-60`。不把 `z` 等非法字符猜测替换成数字；无法提取唯一标识时整批拒绝上传，不进入自动发信。
- 文件名主体是 MAC 时，规范化大小写和分隔符后匹配数据库。
- 可支持完整的 12 位十六进制、短横线或下划线分隔的 6 组两位十六进制；具体按实际文件样例确认。
- 上传的 `.lic` 及 ZIP 内 `.lic` 可带额外前后缀，但必须包含且只包含一个可识别的 `new_pds_<12位MAC>.lic` 或 `new_pds_<12位MAC>_floating.lic` 标识；系统规范化为标准文件名后匹配。无标识或同时包含多个标识时整批拒绝，不进入自动发放。
- 一个 MAC 必须唯一对应一条仍需发放的有效申请。同一 MAC 多条申请、续期或重复申请时，不自动选择最新一条。
- 当前已拒绝的申请不可发放。旧“已通过”也不能直接视为已发送；历史记录首次上线前需核对处理范围。
- 现有 status=0/1 的申请可能已在线下审批并拿到文件，不能仅因未在旧后台改成“已通过”就全部拦截；具体历史状态映射在审阅脚本后确定。夜间发放依赖 FAE 上传的交付文件及明确的有效申请范围，不新增在线审批流程。

“校对”首版是文件完整性、文件名 MAC、申请归属、收件邮箱和重复发放检查。文件名不能证明文件内部的授权类型、年限或版本正确；没有真实格式规则前，不宣称完成授权内容校验。

### 自动发送条件

- 文件完整且通过允许的基础格式检查。
- 能唯一关联有效申请，没有同批冲突或待确认替换。
- 申请邮箱格式有效，且收件人、申请关键字段在处理期间未变化。
- 该申请的本次发放尚未成功，当前没有另一个任务占用。

正常项独立发送，异常项不阻塞同批其他邮件。无法匹配、多个候选、同一申请多个不同文件、无效邮箱等进入异常列表，写明原因。

每条申请单独发信，只附其对应文件；默认不将多个客户放入一封邮件。邮件包含申请编号、必要授权摘要、附件以及统一 FAE 的联系信息。

## 5. 重复上传、补发与发送结果

- 同一申请重复上传相同内容：提示已有文件，不增加重复发送任务。
- 同一申请上传不同文件：作为待确认替换，不自动覆盖，不让旧新文件竞争发放。
- 已经发送过的申请：新上传不自动触发补发；通过明确“重新发放”操作创建新记录。
- 发送服务明确拒绝或尚未尝试发送的暂时故障：按配置重试并限制次数。
- 超时等结果不明：标记“发送结果待核查”，优先查邮件服务记录，不能直接当失败无限重试。
- 服务已接受邮件：记为“发送服务已接受”；是否送达、退信是另外的事件，不把接口成功等同客户收到。
- 若发信成功后记录回写失败，任务恢复时进入结果核查，不能凭数据库缺少成功标记就重新发送。优先选择支持请求去重或结果查询的邮件渠道；普通 SMTP 无法保证严格只发送一次，需保留人工核查路径。

夜间任务结束后给 FAE 一封批次结果汇总：成功、失败、待核查和匹配异常数量，以及后台入口。是否同时抄送每封客户邮件由配置决定，默认仅汇总，减少 FAE 收件噪声。

## 7. 技术边界

本次必要改动集中在管理后台、文件存储、持久化任务与邮件发送服务。客户 Web 和小程序继续使用现有申请页，无需为了邮件自动发放改版。

建议 License 匹配与发放规则集中在一个服务中，并让现有脚本调用该服务的受限接口。如果选择 Java 业务后端承载，Node 后台改为代理相关写入，旧 Java/Node 任意状态修改入口同步收口；避免两个服务各自判断是否发放。

建议新增上传批次、文件记录、申请文件关联、邮件发放记录、任务记录及操作日志。申请 status 按用户最新四状态定义推进，邮件发送结果单独记录；旧早间脚本需替换，历史状态需核对后迁移。

任务需要：持久化记录、唯一业务键、领取锁、超时恢复、申请版本核对和进程重启恢复。先使用现有 MySQL 即可，不必首版引入额外消息队列。

上传和文件查询沿用内部后台身份验证。邮件账号和凭据只放服务端配置，不进入前端或 Git。客户附件按申请关联选择，禁止通过不受控文件名拼接本地路径。

时区统一配置 Asia/Shanghai。定时任务不依赖 FAE 浏览器保持打开；在服务器进程或现有计划任务中运行。设计中只规定调度行为，本文不创建实际任务。

## 10. 已提供脚本的检查结论

来源：用户提供 license-notify-code.tar.gz，含 run-daily.sh、license_notify.py、mail_client.py、status.sh、test_license_notify.py、README.md。原始文件保留不变，本次未连接生产数据库或邮件服务。

### 可复用部分

- run-daily.sh 调用 python3 license_notify.py run --once --digest，使用目录/PID 锁避免常规并发执行。
- 通知状态与日志位于 /var/lib/pango-license-notify/，脚本不更新业务表。
- license_notify.py 从配置读取 MySQL 和 SMTP 参数，生成 HTML/纯文本申请表；汇总超过一条时附带 CSV。
- mail_client.py 已有 SMTP 连接、认证、附件构建、动态收件人和 Reply-To 支持，可作为客户邮件的底层发送基础。
- 本次包中没有 .env，尚不能确认线上实际发件人、端口、FAE 收件人或邮件渠道限制；无需用户把密码发到会话中。
- run-daily.sh 自身未写死 09:00，真正调度时间在服务器计划任务中，09:00 目前依据用户说明。

### 与夜间发放必须分开的部分

- 原 state.json 的 last_notified_id 只表示申请是否已经通知 FAE，不代表审批、License 上传或客户发放。
- 原 Mailer 默认使用配置里的 LICENSE_NOTIFY_TO/CC，不能原样拿来发客户附件，否则仍会发给 FAE。客户邮件必须显式选择申请邮箱；FAE 汇总与客户邮件模板、收件人规则各自独立。
- 原通知逻辑只读数据库；客户发放需新增持久化文件关联、任务和发送记录，原只读账号不能直接承担这些写入。为新执行器提供受限业务接口或专用最小写权限。
- 原发送逻辑捕获全部异常后重试一次。客户发放不能照搬：SMTP 返回前后断线可能使结果不明；成功后本地状态保存失败也可能导致重复发送。
- 原脚本可能按查询批次生成多封汇总，--digest 并不在任意数据量下保证只有一封；如需固定每天一封，应一起处理批次聚合和单轮上限。

### 建议实施组织

保留早间 run-daily.sh 及其通知状态文件；增加独立夜间执行入口（名称暂定 run-nightly.sh）和客户发放任务，复用 mail_client.py 的底层连接能力。早晚任务独立记账，不共用 last_notified_id。

后台负责上传暂存、匹配展示和异常处理；一个统一的业务服务管理最终匹配、领取任务和发放结果。夜间执行器通过受限接口领取任务并回写结果，或在确定由同一服务承载后直接执行。避免 Node、Java 和 Python 各保存一套不同的发放状态。

邮件模板、附件归属、重复上传、重复执行、SMTP 结果不明等需要补充专门测试；现有通知测试不能代替客户发放验收。

离线验证：现有测试共 178 条断言通过，执行时阻止网络连接，未发邮件。初次执行有两条 macOS 临时目录路径别名导致的断言失败，改用规范化临时目录 /private/tmp 后全部通过，未修改原始代码。此结果不代表已验证线上 SMTP 或数据库连通性。

## 11. 第一版实现落点

本版按最后确认的简化流程实现于 `Pango-Admin-Console`：Node 模块统一负责匹配与发放状态，Python 仅复用 SMTP 连接能力，服务器 cron 调用 Node worker。文件内容存入私有 MySQL 表，避免部署切换丢失本地附件。本版没有新增 Java/前端用户中心或线上审批。

已提供早间 digest、夜间 nightly、迁移 migrate 三个 CLI 入口及北京时间调度包装脚本；默认发信关闭。上传 API、异常处理、准备模式提示和发放记录在同一后台内完成。具体权限、部署顺序与首版边界以 `license-delivery-deployment.md` 为准。


## 12. 四状态、时段筛选与拒绝通知

- 申请页按提交日期和四状态组合筛选，结束日期包含当天；文件页按上传日期和文件状态筛选。
- 四状态都可人工设置，同时保留实际通知和上传触发的自动更新；人工设置不会伪造邮件发送结果或上传文件。

- 拒绝通知失败保留已拒绝状态，单独展示邮件失败；结果不明须核查，不盲目重发。
