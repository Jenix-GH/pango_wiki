# Windows 一键上传：License 准备模式

## 本地待发布：取消后重新上传复用原记录

已取消的 License 文件再次上传时，若内容 SHA-256 和 MAC 相同，恢复原记录并重新匹配，不新增条目。原申请关联、邮件及操作历史保留，上传时间更新为本次时间（22:00 后上传的文件进入下一晚）。仍被拒绝、邮箱变化或匹配冲突时不会进入待发放；重试次数不会因重新上传而清零。文件内容不同仍作为新文件处理，避免覆盖不同版本的授权文件。已经存在的历史多条记录不会自动删除。

## 本地待发布：单条立即通知 FAE

入口：后台“License 申请” → 待处理申请的“立即通知 FAE”。确认申请编号及 FAE 邮箱后，平台邮箱只发送这一条申请，使用现有 FAE 汇总模板和 CSV 附件。发送成功后申请转为“处理中”，早上 9 点定时汇总跳过已通知的申请；重复点击也不会重发。

准备模式下也可明确确认后单条发送，不需要启用全部定时邮件。结果不明时需先核查；包含多条申请的失败汇总不能通过单条按钮重发。通知记录在“License 发放”的 FAE 通知记录中查看。本次只更新后台，无新增数据库迁移。

代码位置：`src/licenseApplications.js` 为按钮；`server.mjs` 的 `POST /license-delivery/applications/:id/workflow` 接收 `action: notify-fae`；`licenseDelivery.mjs` 的 `runApplicationStep()` 与定时 `runDigest()` 共用 `dispatchDigest()` 和发送记录。

## v5.3.2：只更新后台，选中文件立即发送

本轮不更新 Web、小程序、Java，也没有新数据库迁移。使用新版 CMD 部署并保留原私有配置。

入口：“License 发放”列表 → 找到已匹配文件 → “查看 / 处理” → “立即发送”。

1. 从现有前端用自己的邮箱和真实 MAC 提交申请；FAE 通知仍按原定时流程执行。
2. 在后台上传并匹配对应的真实 License。已经上传匹配的文件可直接进入下一步。
3. 打开这份文件的“查看 / 处理”，点击“立即发送”，核对弹窗中的申请编号、附件名、FAE 发件邮箱和申请人收件邮箱后确认。
4. 系统立即执行与夜间任务共用的文件完整性、匹配、申请信息及去重校验，使用 FAE 邮箱发送实际附件，并写入正式发放记录。
5. 检查收件箱和附件；SMTP 接受不等于实际送达。成功后状态显示“邮件服务已接受”，22 点任务不会再重复发放该申请。

准备模式也允许明确确认的单条发送，不必打开全局发送开关。此按钮只处理选中的文件及其关联申请，不处理其他队列。重复点击不能绕过去重；暂停、冲突、拒绝、结果不明或重试超限时需先核查。已成功发放的文件不显示“立即发送”。

这验证真实申请、上传匹配、邮件发放与状态记录，不会安装/启动 cron，也不能证明服务器定时任务已正确调度。FAE 汇总通知与 cron 时刻触发仍需另行验收。本版没有清空历史记录、批量修改历史状态或自动设置历史分界；旧脚本/人工发信记录缺失的历史申请仍需按部署说明核对。

使用完整的新版 Pango-Admin-Console 文件夹。将原本地 `deploy/upload-admin-console.psd1` 按相同路径放回，保留 SSH 地址、RemotePath、Pm2ProcessName、IdentityFile 等真实值；不要用 example 文件覆盖原配置。然后双击 `upload-admin-console.cmd`。CMD 仍是入口，实际逻辑在 PS1、同目录 shell 文件和 scripts 下的部署检查程序，不能只替换 CMD。

## 自动执行

1. 本地检查并打包后台源码；不上传本地数据库配置或邮箱密码。
2. 服务器临时目录安装依赖、构建，核对 PM2 目录与默认配置的使用方式。
3. 读取原服务器数据库配置，检查原申请表及七张工作流表；缺失工作流表时先备份数据库，再补建缺表。只执行管理后台三份建表 SQL，不清空数据、不改变原申请状态。
4. 新版本配置设为工作流已启用、邮件发送关闭，保留其他配置值。
5. 重启 PM2，验证新网页和认证接口。失败恢复旧代码/配置，成功也保留旧工程备份。

成功后页面应显示“准备模式”，可以设置状态、填写拒绝理由和批量上传。邮件仍待排队。实际邮件配置、历史通知核对及新旧定时任务切换另行安排。

## 停止时如何处理

- 缺少 mysqldump：在管理后台服务器安装与 MySQL 版本兼容的客户端，或由 DBA 先备份并执行三份建表 SQL，再重新运行。数据库可以在另一台服务器，连接地址取自原配置。
- 数据库备份失败或 CREATE 权限不足：请 DBA 核对权限，或由 DBA 先完成迁移。不要把高权限密码粘贴到对话中；不要给前端配置数据库密码。
- 已有表缺字段/索引：DBA 检查结构后修复，脚本不会覆盖旧表。
- max_allowed_packet 太小：DBA 调整至至少 16 MB 后重试。
- PM2 目录不符、使用自定义配置或已开启邮件发送：按提示核对原服务和调度；不要通过修改示例路径强行跳过检查。
- 准备失败发生在切换前，原后台仍运行。MySQL DDL 不支持事务回滚，权限失败前已创建的表可能保留，重跑会跳过这些完整表。

## 回滚和范围

原工程及配置备份在部署目录同级 `.pango-admin-backup-<发布编号>`；缺表时生成的数据库备份在 `.pango-admin-database-backup-<发布编号>/database.sql`。成功日志输出实际位置。这些备份不会自动删除，后续由运维按保留策略清理。启动失败的新版可能留在 `.pango-admin-failed-<发布编号>`。

人工回退先暂停新发信任务，恢复指定旧工程及配置，再按原 PM2 启动方式运行。保留数据库新表、申请、附件及邮件去重记录；不要直接用上线前整库备份覆盖上线后的业务库。不要未经历史通知核对就恢复旧发信任务。

本脚本只部署管理后台。Java 个人中心的两列及索引迁移、Java 服务、Web、小程序仍按各自交接说明处理。服务器需要 node/npm/PM2/flock，缺表时还需 mysqldump。Windows 需要原有 PowerShell、OpenSSH、tar、Node/npm 及后台本地测试依赖 Python 3；初次使用完整源码请先在后台目录运行 npm ci。
